# PostgreSQL local — étape 4 (pilote historique et mois NOAA, 2026-11-06)

**Usage strictement local.** La base et son volume Docker contiennent des positions, identifiants et noms de navires ; ne jamais les exporter vers GitHub ou Hugging Face, ni exposer le port publiquement. Le chargeur refuse explicitement une `DATABASE_URL` pointant hors de la boucle locale (`127.0.0.1`, `localhost` ou `::1`). Aucun flux AISStream réel n'a été capturé faute de clé. Le **premier pilote historique** était une journée ; depuis le 2026-11-06, le mois NOAA complet est chargé dans la même base privée, sans trajectoires mondiales.

## Démarrage, secret, chargement

1. Installer Docker Compose et Python 3.11–3.14 ; installer les dépendances du `pyproject.toml` (`psycopg[binary]`, `pyarrow`, `pytest` pour les tests).
2. Copier `.env.example` vers `.env` **non suivi par Git** ; définir `POSTGRES_PASSWORD` fort, puis `DATABASE_URL=postgresql://ais_user:<mot-de-passe-encodé-URL>@127.0.0.1:5432/ais_pipeline` avec **le même** mot de passe. Garder `.env` en mode 0600. Les valeurs de `.env.example` sont des placeholders, jamais des secrets. Option `POSTGRES_PORT` si le port local 5432 est occupé (modifier aussi DATABASE_URL). Pour la commande de l'étape 4, ce fichier doit contenir des **affectations valides pour le shell** : protéger/quotter les valeurs ayant des caractères spéciaux pour le shell. **Ne sourcer que son propre `.env` de confiance** : sourcer un fichier exécute son contenu comme du code.
3. `docker compose up -d --wait postgres` : image PostgreSQL 16, port lié à **127.0.0.1 uniquement** ; `sql/schema.sql` initialise les tables au premier démarrage **sur volume vide**. Sur un volume préexistant, appliquer les changements de schéma explicitement via psql/migration avant chargement ; ne pas supprimer un volume contenant des données par erreur.
4. **Docker Compose lit `.env`, mais Python ne le lit pas automatiquement.** Depuis la racine du dépôt, charger `DATABASE_URL` dans un sous-shell, sans coller le secret dans la commande ni le laisser exporté après exécution :

   ```sh
   (
     . ./.env && export DATABASE_URL && \
       .venv/bin/python -m scripts.load.postgres \
         data/processed/source/noaa/manifests/2024-01-14-ny-nj.json
   )
   ```

   Seule `DATABASE_URL` est exportée au processus Python ; les autres variables de `.env` restent locales au sous-shell, sous réserve qu'elles ne soient pas déjà exportées. Charger un manifeste produit par la transformation. Le programme valide SHA-256/provenance de l'entrée brute et du Parquet, le schéma, la partition, le `source` et le type cargo ; il ne charge pas le JSONL directement. Il écrit par lots de 5 000 au maximum dans **une transaction par manifeste**, avec clés étrangères et `ON CONFLICT`. Deuxième exécution inchangée = **0 insertion**. Un test d'intégration injecte une deuxième ligne invalide après un premier lot valide et confirme le rollback total (0 observation, 0 navire, 0 lot). Si un lot déjà chargé change, erreur bloquante : reconstruire la base de façon contrôlée au lieu de laisser d'anciennes observations orphelines.
5. Pour une capture AISStream locale terminée, utiliser uniquement son manifeste `data/processed/source/aisstream/manifests/<session>.json`. Les clés `(source_code,mmsi)` isolent les identifiants des deux sources. MMSI est un émetteur, non une identité permanente ; le suivi est discontinu.
6. Agrégats : `--aggregate data/processed/noaa_candidate/YYYY-MM-ny-nj.parquet` n'accepte **que** le candidat NOAA local ; il revalide l'intégralité du mois et les seuils avant chargement dans `noaa_aggregates`. Le candidat de janvier est désormais **aussi chargé dans PostgreSQL local**. Ni ce chargement, ni une ligne dans cette table ne publient quoi que ce soit ou ne lèvent la revue humaine et le blocage des droits Hub.
7. `docker compose stop postgres` pour suspendre la base ; **ne jamais** lancer `docker compose down -v` si les données doivent être conservées.

`sql/analyses.sql` contient cinq requêtes exécutables (pas de vues publiques) : 01 jointure + décompte journalier source ; 02 fenêtre `LAG` et ruptures >6 h ; 03 CTE + classement `DENSE_RANK` des MMSI observés ; 04 qualité et types par source ; 05 rapprochement privé avec un agrégat NOAA candidat éventuel. Les ruptures et changements de MMSI empêchent d'inférer des voyages complets. L'analyse 03 **affiche les MMSI** : ne pas partager ses résultats. `sql/indexes.sql` contient un index optionnel source/temps pour les fenêtres de requête ; `sql/benchmark.sql` reprend la forme de l'analyse 01 sur **une heure UTC** pour une comparaison avant/après.

## Mesures historiques (base du premier pilote NOAA du 2024-01-14 uniquement)

PostgreSQL **16.15** local, 22 235 observations cargo, 35 MMSI distincts (pas nécessairement 35 navires), une entrée `ingestion_batches`, 0 agrégat, 0 AISStream ; table `observations` **3 792 KiB** (`pg_relation_size`). Premier chargement : **6,92 s** mesurés avec `time.perf_counter` incluant validation des SHA/connexion/transfert ; second chargement : **0,15 s**, 0 insertion et toujours 22 235 lignes. Les cinq requêtes ont été exécutées **sur la base historique ne contenant alors que le 2024-01-14**, avant collecte des autres journées : respectivement **1, 1, 5, 4, 0** lignes de résultat. La cinquième était vide parce qu'aucun agrégat mensuel n'avait été chargé en base. Depuis, le candidat de janvier a été chargé **en plus** dans `noaa_aggregates` avec les 30 autres journées NOAA détaillées ; les mesures de ce paragraphe restent **historiques, avant le chargement mensuel**, et ne concernent donc pas le mois complet.

`ANALYZE observations` suivi d'un échauffement puis trois `EXPLAIN (ANALYZE, BUFFERS)` identiques sur `sql/benchmark.sql`, même processus/connexion et filtre **2024-01-14 12:00–13:00 UTC**, 983 lignes ; timings *Execution Time* en ms :

| État | Plan sur `observations` | Temps (trois exécutions) | Blocs partagés touchés (premier plan reporté) |
| --- | --- | --- | --- |
| Avant index | Seq Scan ; 21 252 lignes écartées | 1,458 ; 1,443 ; 1,432 | 476 hit |
| Après `sql/indexes.sql` | Bitmap Index Scan + Bitmap Heap Scan ; 983 lignes retenues | 0,559 ; 0,554 ; 0,569 | 29 hit |

Index `observations_source_time_idx` **679 936 octets** ; médianes 1,443 ms vs 0,559 ms (**~2,58× sur cette fenêtre et ce cache**, pas une promesse de gain sur une journée entière ou un autre volume). Cette comparaison n'isole pas tous les effets du cache/de la planification et n'inclut pas le temps de réseau/chargement. Vérifier à nouveau `EXPLAIN` sur le corpus final ; sur une plage couvrant presque toute la table, PostgreSQL peut préférer un Seq Scan.

## Mesures du mois NOAA chargé (base pilote conservée, 2026-11-06)

Avant chargement, **98 Go libres** sur le système de fichiers, conteneur PostgreSQL `running/healthy` avec port publié **127.0.0.1:5432** seulement, `DATABASE_URL` vérifiée sur la base locale `ais_pipeline` (secret non affiché), 31 manifestes NOAA journaliers, checksums/partitions et candidat mensuel validés **en lecture seule**. Le lot historique du 14 était déjà présent : le chargeur existant a chargé les **30 jours manquants** en transactions par manifeste, sans `TRUNCATE`, réinitialisation, nouvelle collecte ni AISStream. Premier passage des 31 manifestes : **760 368 nouvelles observations en 68,94 s** au total (`time.perf_counter` du client, validation/hachage et transfert compris), le 14 a inséré **0** ; contrôle de provenance du candidat et insertion de l'agrégat ont porté la durée totale à **89,93 s**. Ces temps reflètent cette machine, cache et base, non une vitesse d'ingestion garantie.

Contrôle SQL après chargement et après reprise : **31 lots NOAA distincts**, **31 dates**, **782 603 observations NOAA détaillées** (dont **51** `implausible_jump`/`conflicting_position` exclues des totaux candidats), **782 552** points admissibles et **315 émetteurs MMSI distincts** admissibles, mêmes deux totaux dans l'unique ligne `noaa_aggregates` du mois et dans le Parquet candidat ; SHA-256 du candidat concordant. **0** observation AISStream. Deuxième passage des 31 manifestes : **0** insertion en **3,73 s** ; revalidation/UPSERT local du candidat : état inchangé (**31 lots / 782 603 points / 1 agrégat**), **26,63 s** pour cette seconde passe totale. L'UPSERT peut réécrire physiquement l'unique ligne : « idempotent » signifie ici valeurs/totaux stables, pas zéro écriture SQL.

Les **cinq requêtes** de `sql/analyses.sql` ont été exécutées, sans exposer leurs résultats individuels (l'analyse 03 contient des MMSI) : **1, 31, 5, 17, 1** lignes respectivement. La cinquième compare maintenant une ligne privée réellement présente et des totaux concordants. Temps client d'**une seule** exécution : ~18, 965, 71, 684, 537 ms dans cet ordre ; ce ne sont **pas** des benchmarks statistiques, et les cinq analyses n'ont pas la même fenêtre de temps. Ne jamais rediriger leur sortie complète vers un journal partagé.

Après `ANALYZE observations` puis échauffement et trois `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` sur `sql/benchmark.sql` (toujours **une heure** du 14, **983 lignes**), le plan utilise `Index Scan` sur `observations_source_time_idx` : **0,585 / 0,581 / 0,576 ms**, 28 blocs en cache, 0 lecture disque lors du dernier plan. L'index occupe **30 162 944 octets** ; la table `observations` seule, **136 413 184 octets**. Sur un **comptage du mois complet**, après échauffement, **35,454 / 30,760 / 35,680 ms** : PostgreSQL privilégie le `Seq Scan` (parallélisé), **pas** le même index. Ces mesures serveur sont à cache et machine locaux ; l'ancien facteur ~2,58× (ci-dessus) a été obtenu **avant chargement sur une base d'une journée**. Nous n'avons **pas** de mesure avant index sur le volume mensuel et ne prétendons **pas** mesurer son gain sur le mois.

Tests : `pytest -q` sans DB saute uniquement l'intégration ; pour l'intégration, créer une **base dédiée dont le nom finit en `_test`**, y appliquer `sql/schema.sql`, fournir `TEST_DATABASE_URL` et exécuter `pytest -q` (les tests tronquent les tables de **cette base dédiée**, jamais la base pilote). Ne pas mettre les URL contenant un mot de passe dans Git ou dans un historique de commandes partagé.
